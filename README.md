# Customer Intelligence & Experimentation Platform

[![Python](https://img.shields.io/badge/Python-3.11+-blue)](#) [![PySpark](https://img.shields.io/badge/PySpark-ETL-orange)](#) [![PostgreSQL](https://img.shields.io/badge/PostgreSQL-Analytics-blue)](#) [![FastAPI](https://img.shields.io/badge/FastAPI-Serving-green)](#)

A production-minded applied data-science project answering four questions every product business cares about:

> **Who will churn? What will they spend? What type of customer are they? Did our intervention actually work?**

This repository demonstrates the lifecycle beyond `model.fit()`: **distributed ETL, SQL, data quality, feature engineering, supervised/unsupervised ML, causal experimentation, explainability, experiment tracking, API serving, and monitoring.**

## Architecture

```text
Raw customers / events / transactions / experiments
                  |
                  v
        PySpark ETL + quality gates
     dedupe | schema | timestamps | joins
       7/30/90d windows | RFM | trends
                  |
          Parquet feature mart
                  |
        PostgreSQL analytical layer
      cohorts | features | experiment SQL
                  |
      +-----------+------------+
      |           |            |
    Churn       Value      Segmentation
 LR/RF/XGB   EN/RF/XGB    K-Means + PCA
      |           |            |
      +------ MLflow + SHAP ---+
                  |
       A/B testing / power / CI
                  |
        FastAPI + monitoring
                  |
       grounded insight summary
```

### Why PySpark?
Spark is not a resume-only dependency here. `src/etl/spark_etl.py` owns event-scale transformation: deduplication, referential-integrity checks, impossible-timestamp checks, 7/30/90-day aggregations, behavioral trend features, transaction features, multi-table joins, and Parquet materialization. Modeling intentionally remains in scikit-learn/XGBoost, which is the better fit after reducing raw events to a customer-level feature table.

## Modeling problems

| Problem | Models / methods | Evaluation |
|---|---|---|
| Churn | Logistic Regression, Random Forest, XGBoost | ROC-AUC, PR-AUC, F1, precision, recall, Brier score |
| 30-day value | Elastic Net, Random Forest, XGBoost | MAE, RMSE, R² |
| Segmentation | K-Means + PCA | Behavioral cluster profiles |
| Retention experiment | two-proportion inference + statsmodels power | lift, 95% CI, p-value, power, segment effects |

Every metric in `artifacts/` is generated by the pipeline; none are hard-coded.

## Data engineering & quality

The normalized source layer contains `customers`, `events`, `transactions`, and `experiments`. Spark validates duplicate IDs, orphan foreign keys, negative transaction amounts, and future/impossible timestamps before building features. PostgreSQL scripts add a second, inspectable SQL layer for cohort analysis, customer features, and experiment metrics.

Generated Spark outputs:

```text
data/spark/customer_features/          # partition-friendly Parquet feature mart
data/processed/customer_features_spark.csv
artifacts/spark_data_quality.json
```

## MLflow + SHAP

Training logs each model family and its metrics to local MLflow tracking. Start the UI with:

```bash
make mlflow
```

SHAP generates global feature-importance artifacts for the deployed churn/value models:

```bash
make explain
```

Outputs live in `artifacts/*_shap_importance.csv` and `reports/figures/*_shap_summary.png`.

## Experimentation

The randomized retention campaign analysis calculates control/treatment conversion, absolute and relative lift, confidence intervals, statistical significance, required sample size, and heterogeneous segment effects. The rollout rule requires statistical significance **and** a positive lower 95% CI bound. Segment effects are explicitly exploratory unless multiplicity controls or pre-registration are added.

The AI component never calculates statistics. `src/insights/grounded_summary.py` turns already-calculated results into a constrained prompt for executive interpretation.

## Run locally

Prerequisites: Python 3.11+, Java 17+ for Spark, and Docker if using PostgreSQL.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
make full
```

For the lightweight non-Spark workflow:

```bash
make run
```

Then serve the API:

```bash
make api
# http://localhost:8000/docs
```

PostgreSQL:

```bash
docker compose up -d db
psql postgresql://postgres:postgres@localhost:5432/customer_intelligence -f sql/schema.sql
```

## Current reproducible baseline

The included fixed-seed synthetic run contains **5,000 customers, 38,422 events, and 6,219 transactions**. In the baseline artifacts, Logistic Regression leads churn ROC-AUC at **0.7572**; Random Forest leads value prediction with **RMSE 12.61 and R² 0.9004**. The simulated retention campaign moves conversion from **39.23% to 42.94%**, an absolute lift of **3.70 percentage points** (95% CI **0.98–6.43 pp**, p=**0.0078**). Re-run the pipeline whenever the data generator or feature logic changes; treat generated artifacts as the source of truth.

## What to discuss in an interview

The strongest design decision is separation of concerns: Spark handles high-volume event transformation; SQL makes analytical logic auditable; Python handles model development and statistical inference; MLflow provides experiment lineage; SHAP explains deployed predictions; FastAPI creates a serving boundary; monitoring closes the lifecycle. The synthetic dataset is reproducible so the repository runs anywhere, while the architecture can accept a real source dataset without changing those boundaries.
